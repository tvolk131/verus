# Loops produced by Rust macros

A `macro_rules!` expansion runs after an enclosing `verus!` or native function
attribute has visited its input. A `for` loop generated by that expansion can
therefore reach the frontend without Verus's loop translation. If the diagnostic
asks for `verus_exec_expr!`, put that wrapper **inside the macro's expansion,
around the generated loop**, not merely around the macro invocation:

```rust
{{#include ../../../../examples/guide/macro_loop_adapter.rs}}
```

This example ordinarily verifies `result == limit` for every `u32` limit, with
an authored loop invariant and no inferred contract or assistance. The wrapper
is available from `vstd::prelude::*`; use the matching compiler, macros and vstd.
It is an existing syntax adapter, not a new inference profile or a trusted
implementation model. The macro definition must be editable; wrapping a call
does not recursively visit tokens generated later by an opaque dependency macro.
Each nested macro which generates a loop needs its own syntax-processing boundary.

During native erasure, `verus_exec_expr!` retains the executable loop and removes
proof syntax, including the example's invariant. Keep the real macro dependency
available to the native build; do not replace it with a hand-written identity
macro when testing erasure. Finite native tests do not establish a full-domain
proof.

The wrapper fixes a syntax-processing boundary only. Iterator contracts, loop
invariants, safety, termination and the caller's application goal still need
support and proof. It does not extend inference's supported iterator operations,
supply missing invariants or certify an application merely because a loop parses.

The regression tests verify this example ordinarily with `--no-cheating`.
Changing only the returned result produces a postcondition failure, not a
frontend rejection. No engine or trust-policy changes are needed.
