# Concrete decision for further source coupling

The full crash-protocol goal is unachieved. Preserve it; do not redefine success around the accepted components. The bounded work authorized by the current charter has produced a real source-selector theorem, checked backend body context, conditional persistence laws, finite native failure coverage and independent review. The next missing kind of evidence is actual native lock/cache/write-trace correspondence.

## Proposed exception, not authorized or started

One isolated,45-active-minute **feasibility experiment** could examine whether the existing checked internal-nominal/source-body facilities can bind an unchanged native std Mutex guard to its actual protected value and release/update state, without a trusted library summary or replacement runtime type. This is an exception to the current prohibition on automatically starting new private-representation/state semantics. It is not promised feasible and does not complete crash safety by itself.

Inputs would be the same accepted78 toolchain, exact std/compiler source identities and REDB's actual std lock use; no new Coq/Iris/Miri dependency or general foreign-MIR program. Freeze the original minimal lock body, type/layout/borrow boundary, existing baseline rejection and exact proposed proof relation before trials. Work only in an isolated research subtree until any concrete compiler change can be reviewed separately.

Required success would be a genuinely checked original-native correspondence for lock acquisition, guard data identity, allowed mutation and restoration/release, with normal lifetime/trait/WF/body/erasure checks; full source/type identity; no added client premise that already asserts the desired guard value; and negative controls that reject a wrong value/frame. Opaque type admission, an assumed Mutex::lock specification, a logical model unrelated to native storage, runtime tests or a synthetic permission supplied by the client would be failure to meet this target. No production fact would be enabled before independent review. If this needs another unsupported primitive/foundation, stop at the first blocker and report it rather than extending a chain.

The application-value gate after any success is the actual PagedCachedFile::flush_write_buffer obligation: every relevant entry buffer is successfully submitted before a successful barrier, with correct bytes, no invented cache frame and all error edges. Failure to reach that gate cannot count as a substantial application improvement. Header clone/serialization, public return/epilogue, candidate retention and complete recovery remain separate unfinished requirements even if a guard bridge succeeds.

The other choice is to retain the current no-foundation restriction and hold the full goal as unachieved at this reviewed checkpoint until suitable source-effect support exists or the user changes scope. No trusted backend/lock law is proposed under either choice. No implementation of this exception has started. HMAC/native remains DEFERRED AND UNACHIEVED.
