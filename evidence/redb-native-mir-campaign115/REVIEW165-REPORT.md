## F165-1 — P2: serialized-opcode quarantine scans only the body

**Exact location:** `candidate/source/vir/src/native_resource.rs:14`; the added fallback at line16 calls `adapter164::contains_native_call` only on `function.x.body`. `candidate/source/vir/src/native_resource/adapter164.rs:41` correctly traverses the expression it is given, but receives no function contracts or other expression-bearing fields. The enum is always serializable (`candidate/source/vir/src/ast.rs:1026`).

**Source-structural counterexample:** take an unmarked serialized Function with `body: None`, remove `attrs.infer_candidate_id`, and place a NativeAllocator164 expression in an expression-bearing contract field, for example a Block statement followed by `true` in `require`, or a `fndef_axioms` expression. `is_marked` necessarily returns false: both of its tests are false regardless of the opcode in the other field. `reject_crate` therefore does not refuse this function at the import/export/native-admission quarantine. Import calls it immediately after deserialization (`candidate/source/rust_verify/src/import_export.rs:111` and :116); export calls it at :275; native-source admission calls it at `candidate/source/rust_verify/src/verifier.rs:2914`. This counterexample is derived from those branches, not compiled, serialized or executed by this review.

**Consequence and severity:** the explicit marker-independent transport refusal is incomplete. A serialized new opcode can cross that particular gate even with the adapter feature off. The regression at `adapter164.rs:165` only serializes an Expr and calls the body-expression detector; it does not test a whole Function whose opcode is outside its body. This is a P2 quarantine/defense-in-depth defect, not evidence of usable allocator authority or a demonstrated theorem-soundness bypass.

**Counterarguments and limits:** a normally generated well-moded contract cannot call this exec opcode; modes rejects non-exec uses (`candidate/source/vir/src/modes.rs:2022`). `validate_call` still rejects disabled operation (`adapter164.rs:29`), canonical AST-to-SST still checks the resource types (`ast_to_sst.rs:1870`), and every resulting SST opcode still fails AIR (`sst_to_air.rs:1839`). Those barriers prevent promotion of this finding to P1. They do not make the import/export detector's answer correct, particularly for serialized input before local mode checking. No claim is made that an honestly produced well-formed164 artifact currently exploits the gap.

**Smallest exact repair:** retain the attribute-prefix test, but replace the body-only fallback with a whole-function opcode visitor. The existing canonical visitor already walks require, both ensure lists, returns, decreases/decrease_when, mask/atomic/unwind expressions, body, and fndef_axioms (`candidate/source/vir/src/ast_visitor.rs:1218`, :1230, :1245). A new helper in adapter164 can use it without changing lowering or adding semantics:

```rust
pub fn function_contains_native_call(function: &Function) -> bool {
    let mut scope = air::scope_map::ScopeMap::new();
    matches!(
        crate::ast_visitor::function_visitor_dfs(function, &mut scope, &mut |_, expr| {
            if matches!(&expr.x, ExprX::Call { target: CallTarget::NativeAllocator164, .. }) {
                VisitorControlFlow::Stop(())
            } else {
                VisitorControlFlow::Recurse
            }
        }),
        VisitorControlFlow::Stop(())
    )
}
```

Then change only `is_marked`'s second disjunct to `adapter164::function_contains_native_call(function)`. Keep the expression detector for the review harness if desired. Add future regression cases for unmarked whole Functions, especially body-less require/ensure/fndef_axioms, asserting `reject_crate` fails for import and export with feature off and on, plus nested-body detection. This repair is a source suggestion only; neither it nor its tests were installed or executed.

## O165-2 — validity/range objection, not a demonstrated defined-input mismatch

`candidate/source/rust_verify/src/native_adapter164/scalar.rs:9` recognizes usize plus core-named Alignment/AlignmentEnum/NonZero with equal pointer-sized layouts. `field_word` additionally checks a sole offset-zero field (:19). Those checks establish the restricted bit-width/field-position conditions actually used by the interpreter; they do not establish equality of each Rust type's valid-bit set.

Both transmute handlers (`candidate/source/rust_verify/src/native_adapter164.rs:211` and `scalar.rs:98`) accept any source/destination pair passing `word_type` and then preserve the numeric expression. The represented values in VIR are just usize; entry parameters carry no Alignment/NonZero validity refinement (`native_adapter164.rs:372`). Consequently the code contains no proof obligation refusing a conversion from arbitrary usize bits to a restricted-validity destination (zero to NonZero/Alignment, or non-power-of-two to Alignment). A source-level unsafe usize-to-Alignment transmute followed by as_usize illustrates the missing safety condition if its MIR takes these supported operations. Its exact compiled MIR and acceptance were not observed here, so it is not a new test result.

**Counterargument accepted:** for defined executions with already valid native operands, equal-width identity interpretation of these word-only operations can be correct. Translating valid Alignment inputs to all usize values overapproximates the input domain; that alone does not create a false equality theorem. A source program exhibiting Rust UB is not an UB-free miscompilation counterexample.164 claims neither an unsafe-code safety theorem nor operative native acceptance. I therefore do not count this objection as a second demonstrated P1/P2 value-correspondence bug.

**Required treatment before operative scalar reuse:** explicitly maintain/check validity refinements or conservatively refuse validity-strengthening transmute pairs. The narrow repair is to permit only checked valid-bit-set-preserving directions (for example valid Alignment to usize, and any required checked Alignment-to-NonZero-to-usize chain) and fail closed on arbitrary usize/NonZero-to-Alignment or usize-to-NonZero unless actual path facts establish validity. Apply the same policy to both handlers; do not simply add an assumed invariant to every input. Add future source/MIR cases for zero, non-power-of-two, permitted maximum alignment, and valid direction conversions. An all-transmute ban is smaller but may unnecessarily remove the real scalar-method subset. No new primitive law is needed or approved.

## Actual scalar interpretation: checks and counterarguments

- **Methods and actual operands.** `native_adapter164.rs:27` resolves the actual FnDef/Instance. `scalar.rs:65` interprets that instance's actual MIR, initializes its sole input with the supplied expression, and recursively reads one actual call argument at :121. It is not a fresh arbitrary numeric result or an equation keyed only by the method name. The name allowlist at :59 is broad, but body/type/statement/terminator checks, depth8 and visited-block32 limits remain in force. A same-name method containing arithmetic, memory, an indirect call or cleanup does not thereby acquire a summary. The allocator-specific selector additionally checks the exact nominal Alignment definition and as_usize signature (`scalar.rs:132`). Ordinary scalar calls do not all pass that special selector; their protection is actual-body interpretation, not the allocator-specific signature check.
- **Constants/equal widths.** Numeric constants come from rustc scalar constant evaluation and actual pointer-size bits (`scalar.rs:48`), not hardcoded8. Native entry refuses non64-bit targets (`native_adapter164.rs:365`). Equal width and offset-zero checks justify retaining this as a pinned scalar bit interpretation, subject to O165-2, not arbitrary layout, enum, pointer or cross-target equivalence. Broad core item-name recognition is not an extensible user-type permission: user crate lookalikes fail the core-crate check. A future toolchain/core change still needs exact review.
- **Ranges/overflow.** Emitted numbers are usize; accepted integer constants originate in64-bit native words. The only accepted binary operations are Eq/Ne on matching usize/bool types (`native_adapter164.rs:226`). Add/sub/mul/shifts, ordered comparisons, checked-overflow tuples and Assert terminators have no supported arm and refuse; there is no wrapping-to-unbounded arithmetic substitution to credit or flag. The corpus's largest usize sample does not test arithmetic overflow. Alignment positivity/power-of-two and allocator layout/size/end bounds are not proved by assigning the usize type.
- **Branch semantics.** SwitchInt lowers the actual discriminant and exact targets into equalities/nested If, validating boolean constants and return-type agreement (`native_adapter164.rs:294`). State is cloned per successor and the entire suffix is lowered separately; no unsupported loop or inter-path phi invariant is invented. Paths with cycles/excessive expansion, cleanup, unsupported terminators or unsupported instructions refuse (:249 and :358). Even syntactically unreachable unsupported successors may cause conservative refusal. That is incompleteness, not unsound success or a totality theorem.
- **Unwind.** Scalar Continue edges are accepted only after recursively interpreting a finite supported body (`scalar.rs:119`; `native_adapter164.rs:346`). In this restricted operations set there is no arbitrary native callee given a blanket no-unwind summary. O165-2 still matters: a validity-invalid transmute is not a nonfaulting safety proof. Allocator calls demand Unreachable unwind, not Continue (:317); no null/error/abort/diverge equivalence is installed.
- **Pointer equality.** The explicit equality type guard refuses pointer/aggregate equality instead of equating native executable addresses with full spec pointers (`native_adapter164.rs:233`). The final negative fixture reaches the earlier pointer-retag refusal, not that equality guard. Both REPORT164 and the preserved35 failure correctly acknowledge this; the equality arm's rejection has source support, not observed end-to-end fixture-path coverage.

No further P1/P2 defect is established in the actual supported, defined scalar value operations by this inspection. This is bounded source review, not a compiler-correctness proof or a claim that every unsupported Rust construct has been tested.
